# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Learning material for using [tididi](https://github.com/Tractables/tididi) circuits as the inference
engine behind ProbLog and DeepProbLog. It is docs, notebooks and two scripts, not a library: no
package, no test suite, no CI. Everything is built around one problem: two handwritten digit images,
labelled only with their sum. Unlike the sibling repos under `Pillar/`, this one is Python, not Rust.

## Environment

This repo has its own `.venv`, separate from tididi's. tididi's Python binding is not on PyPI; it is
built from the sibling checkout `../tididi` with maturin:

```sh
source .venv/bin/activate
python -m pip install -r requirements.txt
(cd ../tididi/bindings/python && maturin develop --release)   # rerun after any tididi Rust change
```

If tididi's API changed upstream, the binding in `.venv` is stale until that line is rerun. The
practice notebook's `draw` helper shells out to Graphviz `dot`.

## Running things

From the repo root, with the venv active:

```sh
python scripts/deepproblog_addition.py   # compiles circuits, self-checks against exact counts, trains 5 epochs
python scripts/make_doc_images.py        # redraws data-based PNGs in docs/images
jupyter nbconvert --to notebook --execute --inplace notebooks/<name>.ipynb   # run a notebook headless
```

`deepproblog_addition.py` has a built-in correctness check (`check_against_exact`): it asserts the
torch-tensor evaluation matches tididi's exact `Fraction` weighted count. Running the script is the
closest thing to a test. Notebooks resolve paths relative to `notebooks/` (e.g. the learning guide
loads `../scripts/deepproblog_addition.py`), so execute them from that directory.

`circuit-sum-1.png` and `circuit-sum-8.png` are tididi `to_dot()` exports relabelled by hand; they
are not regenerated by `make_doc_images.py`.

## Structure: each doc is paired with a notebook

| Doc (`docs/`) | Notebook (`notebooks/`) | Relationship |
| --- | --- | --- |
| `learning-guide.md` | `learning_guide.ipynb` | Cells labelled with the doc's exercise numbers (1a, 2b, …); answers live in the doc |
| `digit-addition-explained.md` | `digit_addition.ipynb` | Doc explains `scripts/deepproblog_addition.py`; notebook solves the problem four ways (by hand, ProbLog, DeepProbLog, tididi) |
| `practice-guide.md` | `practice.ipynb` | Notebook has `TODO` cells and a `check` helper that hides the answer; **answers are only in the doc**, never in the notebook |

When editing one side of a pair, keep the other in sync: exercise numbers, worked-example code, and
the numbers quoted in the doc (e.g. the practice guide's fixed network-output table for images 1–3)
must match what the notebook prints. The README's table lists the reading order.

## The core technique (shared by the script and notebooks)

- Each image's digit is an annotated disjunction: one Boolean variable per digit plus an exactly-one
  constraint. Variable numbering is `1 + slot * N + digit` (image 1 → 1..10, image 2 → 11..20).
- The vtree keeps each image's variables together (`Vtree.join` of two `balanced_over` subtrees).
- One query circuit per sum is compiled once, before training. tididi Boolean ops **consume their
  operands**, so reused circuits are `.copy()`'d before conjoining.
- Training evaluates circuits with a custom algebra (`zero`, `leaf(variable, sign)`, `add`, `mul`)
  whose values are batched torch tensors: positive literal → network probability, negative literal
  → 1, free variable (`sign is None`) → `1 + p`. Autograd flows through the circuit into the network.
- Data is scikit-learn's bundled 8×8 digits (no download). Image pools are split before pairing so
  test pairs never reuse training images.

## Demos (`demos/`)

Separate from the Python learning material and with no tididi. See `demos/README.md`.

- `demos/original/*.html` are the demos as received from their author. They are the
  specification: never edit them. The port must behave identically. Keep the demos as they are;
  do not add tididi.
- `demos/backend/` (Python, uv, FastAPI) holds the engines and the `/api/*` endpoints, including
  the server-side ChatGPT proxy. `demos/frontend/` (TypeScript, Vite) holds only UI code and calls
  the API; there is no engine code in TypeScript.
- Engine ports must reproduce `demos/golden/*.json` exactly. Use the helpers in
  `pillar_demos/js.py`: JS `Math.round` rounds halves up, Python 3.12's `sum` compensates float
  error (use `js_sum`), the RNG is 32-bit `mulberry32`, and number formatting differs.
- Page actions that touch engine state go through the `createSerial` queue in
  `frontend/src/shared/api.ts`. Inside a queued task, call the unqueued helpers, or it deadlocks.
- Gates: in `demos/backend/`, `uv run pytest`, `uv run ruff check .`, `uv run ruff format --check .`;
  in `demos/frontend/`, `npm run typecheck`, `npm run format:check`, `npm run build`, and
  `npm run parity` (needs uvicorn on 8000, `npm run dev`, and `npm run serve:original` running;
  drives the original and the port side by side in headless Chrome).

## Style of the material

Docs and notebooks are written for learners: plain language, exact `Fraction` arithmetic where
possible, and brute-force checkers (enumerate worlds) used to validate every circuit result. Keep
that pattern when adding examples.
